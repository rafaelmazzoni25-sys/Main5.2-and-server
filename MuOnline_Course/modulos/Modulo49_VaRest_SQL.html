Módulo 49 – Implementação Completa do Sistema VaRest + SQL

Passo a passo para expor APIs REST com Node.js, consumi-las via VaRest no cliente UE5 e garantir persistência em SQL de forma compatível com o ecossistema GameServer/DataServer.

Arquitetura Recomendada

Camadas e papéis
  • Cliente UE5 (C++ + Blueprint): usa VaRest para enviar/receber JSON, assina pacotes com token de sessão proveniente do ConnectServer/JoinServer (módulos 2 e 38).
  • Gateway REST (Node.js + Express): valida tokens, traduz JSON em chamadas SQL parametrizadas e mantém logs/metrics.
  • Banco SQL: mesmo schema do DataServer (módulo 9), acessado via pool de conexões (mssql ou mysql2).
  • Sincronização com GameServer: endpoints notificam o GameServer por fila/mensagem (ex.: Redis ou pipe TCP) quando uma alteração deve ser refletida em tempo real.

Preparação do Gateway REST

Ambiente e dependências
  1. Inicialize um projeto Node.js (npm init -y) no diretório de serviços.
  2. Instale express, helmet, cors e compression para servir as APIs.
  3. Adicione o driver SQL correspondente (mssql para SQL Server ou mysql2 para MySQL/MariaDB) e jsonwebtoken para validar tokens.
  4. Configure variáveis de ambiente (.env) com host, usuário, senha, banco e chaves de assinatura de token.
Pool e segurança
  • Crie um pool de conexões com limites mínimos/máximos para replicar o comportamento do DataServer e evitar exaustão de recursos.
  • Habilite prepared statements (consultas parametrizadas) para bloquear SQL Injection.
  • Implemente rate limiting e logs estruturados (ex.: pino) para rastrear chamadas por personagem/conta.
  • Separe credenciais de leitura/escrita se quiser isolar rotas sensíveis (ex.: loja, reset, cash).

APIs Essenciais

Rotas sugeridas
Rota Método Finalidade
/api/auth/session POST Valida token recebido do JoinServer e retorna um JWT curto para o VaRest.
/api/character/state GET Obtém atributos, inventário resumido e posição persistida (similar ao pacote 0xDB do GameServer).
/api/character/save POST Persiste experiência, level, reset e moedas; aceita payload assinado e usa transação SQL.
/api/inventory/update POST Aplica mudanças de slots (drop, venda, compra) e retorna checksum/versão para sincronizar o cliente.
/api/event/log POST Registra participação em eventos (DS/BC/CC/etc.) e premiações, disparando webhook para o GameServer.

Estruture respostas em JSON padronizado ({ success, code, data, checksum }) para facilitar parsing no Blueprint e permitir rollback rápido em caso de falha.

Fluxo no Cliente UE5 com VaRest

Blueprint e C++
  1. Bootstrap: crie um Subsystem (ex.: UCourseRestSubsystem) em C++ que armazena o endpoint base e o token JWT obtido em /api/auth/session.
  2. Requisições: use nós VaRest Request (GET/POST) configurando cabeçalhos Authorization: Bearer <token> e Content-Type: application/json.
  3. Serialização: mapeie structs C++ (ex.: FCharacterStateDto, FInventoryChangeDto) para JSON via UVaRestJsonObject, evitando campos extras.
  4. Resiliência: implemente retries com exponential backoff, timeout de 5–10s e fallback para reconexão de sessão (módulo 38) caso receba HTTP 401/403.
  5. Validação: compare o checksum retornado com hashes locais do inventário/estado antes de aplicar mudanças no cliente.

Persistência e Transações SQL

Padrões críticos
  • Use transações ao salvar progressão e inventário para garantir atomicidade, equivalente ao comportamento do DataServer.
  • Mantenha stored procedures para operações sensíveis (reset, compra Cash Shop, entrega de eventos) e exponha-as via parâmetros nomeados.
  • Calcule hashes/checksums no lado do servidor para detectar corrupção e rejeitar gravações divergentes.
  • Implemente versionamento por registro (coluna row_version) para suportar controle de concorrência otimista.

Sincronização em Tempo Real com GameServer

Feedback imediato
  1. Quando uma rota de escrita for chamada (ex.: /api/inventory/update), publique um evento em Redis ou em uma fila TCP para que o GameServer recarregue o estado do jogador.
  2. Crie um listener no GameServer (thread dedicada) que consome mensagens e chama as mesmas rotinas de atualização já usadas pelos pacotes 0x32/0x3C/0x4F.
  3. Use um campo de versão ou timestamp na mensagem para evitar aplicar alterações antigas.

Testes e Observabilidade

Cobertura mínima
  • Contratos: teste de schema JSON (ex.: com ajv) para cada rota.
  • Integração UE5: automatize chamadas VaRest em AutomationSpec para validar serialização e parsing.
  • Carga: scripts locust/k6 simulando fluxos de login > save > compra para medir latência e saturação do pool SQL.
  • Logs e métricas: exporte contadores de sucesso/falha por rota, tempo de DB e taxa de retry no cliente.

Checklist Final

  • Tokens emitidos pelo JoinServer são aceitos e renovados pelo gateway REST.
  • VaRest envia cabeçalhos corretos e aplica retries com backoff.
  • Queries usam parâmetros, transações e versionamento.
  • GameServer recebe notificações de escrita e aplica mudanças em tempo real.
  • Monitoramento registra latência SQL, erros HTTP e discrepâncias de checksum.
