Módulo 5 – Inventário e Itens

Estruturas de itens no cliente e carregamento/manipulação no servidor.

Pré-requisitos

  • Ter lido os módulos anteriores.
  • Conhecimentos básicos de serialização de itens.

Conceitos do Código Original

Cliente – Estruturas de inventário (ZzzInventory.cpp)
📘 O Que é?

Arquivo que mantém arrays globais de itens, inventário, shop e loja pessoal no cliente.

🎯 Para Que Serve?

Permite ao cliente renderizar e manipular inventários locais (jogador, shop, personal shop) com suporte a slots e dicas.

💻 Como Funciona?

Define múltiplos arrays como Inventory[MAX_INVENTORY], ShopInventory e buffers de loja pessoal. Também mantém itens temporários como PickItem e TargetItem para operações de arrastar/soltar.

ITEM_t Items[MAX_ITEMS];

ITEM g_PersonalShopBackup[MAX_PERSONALSHOP_INVEN];

⏱️ Quando é Executado?

As estruturas são globais e usadas sempre que UI ou lógica de inventário são acessadas (arrastar item, abrir loja etc.).

Servidor – Carregamento de dados de item (CItemManager::Load)
📘 O Que é?

Rotina que lê arquivos de definição de itens e popula ITEM_INFO do servidor.

🎯 Para Que Serve?

Constrói a tabela de atributos (slot, tamanho, serialização, drop) usada em todas as operações de item.

💻 Como Funciona?

Usa CMemScript para ler o arquivo de script, iterando seções e preenchendo campos de ITEM_INFO como index, slot, skill, dimensões e flags. Os registros são armazenados em m_ItemInfo.

void CItemManager::Load(char* path) {
    CMemScript* lpMemScript = new CMemScript;
    if(lpMemScript->SetBuffer(path) == 0) { ... }
    this->m_ItemInfo.clear();

            info.Width = lpMemScript->GetAsNumber();
            info.Height = lpMemScript->GetAsNumber();
            ...
        }
    }
}

⏱️ Quando é Executado?

Invocado na inicialização do servidor, antes de aceitar conexões de jogadores, para carregar dados de item.

Servidor – Operações de item via rede (ProtocolCore)
📘 O Que é?

Entradas específicas no roteador de pacotes que tratam pegar, dropar, mover e usar itens.

🎯 Para Que Serve?

Expõe as operações de inventário para o cliente, respeitando a tabela carregada em CItemManager.

💻 Como Funciona?

Vários cases do switch chamam funções do gItemManager: 0x22 para pegar item, 0x23 para dropar, 0x24 para mover, 0x26 para usar. Cada handler valida slots e atualiza estado do personagem.

case 0x22:
    gItemManager.CGItemGetRecv((PMSG_ITEM_GET_RECV*)lpMsg,aIndex);
    break;
case 0x23:
    gItemManager.CGItemDropRecv((PMSG_ITEM_DROP_RECV*)lpMsg,aIndex);
    break;
case 0x24:
    gItemManager.CGItemMoveRecv((PMSG_ITEM_MOVE_RECV*)lpMsg,aIndex);
    break;
case 0x26:
    gItemManager.CGItemUseRecv((PMSG_ITEM_USE_RECV*)lpMsg,aIndex);
    break;

Servidor – Seleção do drop (item vs. Zen) e opções
📘 O Que é?

Trecho que decide o que cai ao matar um mob: item específico (com opções e sockets) ou dinheiro (Zen), aplicando bônus e tabelas de mapa.

🎯 Para Que Serve?

Reproduz a distribuição de loot 1:1: respeita ItemBag por classe, bônus de drop, Set/Exc, chance de Zen e quantidade.

💻 Como Funciona?

Em gObjMonsterDieGiveItem o servidor verifica ItemBags/quests e, se não dispararem, calcula ItemDropRate e ExcItemDropRate com bônus do player/mapa antes de sortear um índice via gMonsterManager.GetMonsterItem. Se falhar ou não houver item, tenta Zen.

No servidor, ao matar um mob (inclusive bosses), imediatamente antes de enviar o pacote de criação de item/Zen para os jogadores no mapa.

Cliente – Animação e som do drop
📘 O Que é?

Carregamento dos áudios de drop de item e de ouro usados pelo cliente para feedback imediato ao spawnar loot.

🎯 Para Que Serve?

Garantir que o som/efeito ao dropar item ou Zen seja idêntico ao original.

💻 Como Funciona?

Em ZzzOpenData.cpp, os waves pDropItem.wav e pDropMoney.wav são carregados como SOUND_DROP_ITEM01 e SOUND_DROP_GOLD01. O efeito visual usa o BMD do item com animação idle flutuante.

📁 Onde Encontrar?

Source Main 5.2/source/ZzzOpenData.cpp (linhas de LoadWaveFile para SOUND_DROP_ITEM01 e SOUND_DROP_GOLD01).

⏱️ Quando é Executado?

Durante o boot do cliente, antes de entrar no mapa; o som é disparado quando o item/Zen é criado no mundo.

Implementação em Unreal Engine 5

  • Modelar itens como UObjects com UDataAsset para dados estáticos (slot, tamanho, flags).
  • Replicar inventário em APlayerState usando TArray de structs replicáveis; operações são RPCs de servidor.
  • Para looting, implemente um AActor item no mundo com interface de interação, disparando RPC ServerPickupItem.
  • Serialize/deserialize usando FArchive ou FNetSerialize para manter compatibilidade com o protocolo desejado.

Passo a Passo em Unreal Engine 5

  1. Definir um UDataAsset para dados estáticos de item (slot, tamanho, flags, stack) com IDs iguais aos do protocolo original.
  2. Criar struct replicável FItemSlot com NetSerialize e armazená-la em APlayerState para acompanhar o cliente.
  3. Adicionar RPCs para pegar, mover, dropar e usar itens com validação server-side (peso, espaço, requisitos de classe), retornando códigos de erro equivalentes aos handlers C++ originais.
  4. Criar UI de inventário em UMG consumindo os arrays replicados; implementar drag-and-drop com verificação de destino válida antes de enviar RPC.
  5. Persistir inventário via chamada HTTP (VaRest) para Node.js/SQL na entrada e saída do jogador, salvando snapshots de slots e quantidades.
  6. Implementar filtros de equipabilidade por classe/nível replicados do servidor para o cliente, exibindo mensagens específicas quando a operação falhar.
  7. Logar toda operação de item em um painel de debug (e opcionalmente em HTTP) para detectar duplicação ou rollback.
  8. Integrar crafting/combinação simples (se existir no código original) como um RPC adicional, validando componentes antes de gerar o item resultante.
  9. Adicionar testes automatizados de duplicação para garantir que RPCs rejeitam operações concorrentes e que slots não ficam negativos.
  10. Configurar eventos de UI para destacar itens recém-adquiridos e atualizar tooltips com dados do UDataAsset.
  11. Usar FastArraySerializer se o inventário for grande, para otimizar o tráfego replicado mantendo compatibilidade com a estrutura compacta do cliente original.
  12. Documentar o fluxo completo: carregamento de tabelas, entrada do jogador, sincronização inicial do inventário, operações em runtime e persistência ao sair.

Checklist Final

  • Tabelas de item carregadas no início do servidor UE5.
  • Inventário replicado aparece e responde a arrastar/soltar.
  • Operações de loot/drop são confirmadas pelo servidor.
  • Logs mostram mudanças de slots após cada operação.

Tutorial Blueprint (iniciante) com VaRest + SQL

Fluxo completo para quem nunca montou um inventário em UE5. As coordenadas usam viewport 1920x1080; em outras resoluções, deixe os anchors fixos em Bottom-Left e escale proporcionalmente.

  1. Crie os dados: Adicione um PrimaryDataAsset DA_ItemTable com array Items (Id, Nome, RarityColor, Icon, SlotType, Width, Height, StackMax). Preencha com os IDs do script original (ex.: "GET_ITEM(0,0)").
  2. Monte o Blueprint de Inventário: Em Content/UI, crie WBP_Inventory (UserWidget). Adicione um Canvas Panel e posicione um Border em X=68, Y=612, W=620, H=370 (slots 8x5 usando célula de 72 px, bordas de 10 px). Dentro, insira um UniformGridPanel com Slot Padding (4,4) e preencha dinamicamente via CreateWidget de WBP_InventorySlot.
  3. Slot Blueprint: Em WBP_InventorySlot, adicione um Button ocupando 100% da célula, com Image para o ícone e Text para quantidade (fonte 16, alinhado Bottom-Right). Use OnDragDetected para criar um Drag Visual (ícone 64x64) e OnDrop para chamar um evento Server_MoveItem(From, To).
  4. Mapa de arquivos e posições (Inventário/Equip/Shop/Warehouse):
    • /Game/UI/Inventory/WBP_Inventory (Canvas 1920x1080): Border principal em X=68, Y=612, W=620, H=370 com UniformGridPanel 8x5 (célula 72 px, Padding 4). Botões Btn_Sort e Btn_Expand 120x36 alinhados no topo direito do Border.
    • /Game/UI/Inventory/WBP_Equipment (Anchor Top-Left em X=720, Y=120): slots de equipamento 3x4 (72x72, espaçamento 10) nomeados Slot_Weapon, Slot_Shield, Slot_Helm, etc.; painel de atributos rápidos (HP/MP/DEF/ATK) em X=32, Y=340, W=260, H=120.
    • /Game/UI/Inventory/WBP_Warehouse (Canvas 1920x1080): janela modal 980x520 centrada; grid do baú 8x15 (célula 64 px, Padding 2) em X=48, Y=64; lista do inventário do jogador (para transferir) 8x5 em X=48, Y=420; botões Btn_Deposit e Btn_Withdraw 140x40 em X=840, Y=440. Ancore a janela ao centro e bloqueie input de jogo com Set Input Mode UI Only.
    • /Game/UI/Inventory/WBP_NPCShop (Canvas 820x560 ancorado centro): painel esquerdo X=36, Y=42, W=480, H=472 com grid 6x4 (slot 72 px) para lista de compra; painel direito X=540, Y=42, W=240, H=472 mostrando detalhes do item (ícone 96x96, descrição, preço). Botões Btn_Buy e Btn_Sell 160x44 em X=540, Y=460. A abertura deve ser feita pelo overlap em NPC chamando Create Widget (WBP_NPCShop) → Add to Viewport.
  5. Drop 1:1 (servidor → mundo → UI):
    • DataTable DT_DropRules em /Game/Data/DT_DropRules com colunas: MonsterClass, ItemBagId, DropLevelOffset, ItemRate, MoneyRate, MoneyValue, BonusMultiplier. Preencha com valores equivalentes aos de gServerInfo/gMapManager.
    • Actor BP_LootComponent em /Game/Blueprints/Combat: função Server_ResolveDrop (Run on Server) recebe MonsterClass, MapId, MonsterLevel, ItemRate, MoneyRate, MoneyAmountDropRate. Nó Select → Branch decide se chama SpawnItemDrop ou SpawnZenDrop replicando o fluxo de gObjMonsterDieGiveItem.
    • Blueprint BP_ItemDropActor em /Game/Blueprints/World: StaticMesh com Niagara NS_DropFloat e AudioComponent usando AC_DropItem (cue apontando para pDropItem.wav). Para Zen, use AC_DropGold com pDropMoney.wav. Defina Timeline de 0.6s elevando o item 18uu e descendo com easing Ease Out, replicando a animação flutuante.
    • UMG: ao receber OnRep_SpawnedLoot no PlayerController, chame Play Sound 2D (AC_DropItem/AC_DropGold) para manter feedback 1:1. O UI de pickup permanece o mesmo (grid 8x5), apenas reage ao overlap.
  6. RPCs no PlayerController (Blueprint): Declare eventos Custom Event Server_MoveItem, Server_PickupItem e Server_DropItem marcados como Run on Server, Reliable. Cada evento chama uma função Blueprint ValidateSlot (checa se o destino está livre) e, em seguida, atualiza o InventorySlots (array replicado no PlayerState).
  7. Replicação visual imediata: No PlayerState, crie um array InventorySlots de structs (ItemId, Qty) com RepNotify. No OnRep, atualize todos os WBP_InventorySlot com ícones/quantidade. Isso evita gaps de percepção enquanto a resposta do servidor chega.
  8. Persistência via VaRest: No Event BeginPlay do PlayerController, chame VaRest POST para /api/inventory/load com {accountId, characterId}. No OnRequestComplete, converta o JSON em InventorySlots. No EndPlay (ou Logout), envie /api/inventory/save com o snapshot dos slots. Mantenha as rotas compatíveis com o módulo 9.
  9. Tooltips alinhados: Crie WBP_ItemTooltip e mostre em OnHovered do slot. Para reproduzir a HUD clássica, fixe a tooltip com offset (+32, +18) do cursor e largura máxima 320 px; use Wrap Text At para evitar cortes.
  10. Feedback e bloqueios: Adicione Audio Cue de sucesso/erro e um TextBlock de aviso abaixo do grid (Y=992). Bloqueie o botão durante uma operação em trânsito (flag bInventoryBusy) para prevenir duplicação.
  11. Testes guiados: Em Automation, crie um teste funcional que: (1) carrega o mapa, (2) arrasta um item para outro slot, (3) verifica atualização na UI e no array replicado, (4) envia logout e confirma via VaRest que o JSON salvo contém o slot modificado.
  12. Checklist visual: No viewport 1920x1080, confirme: painel do inventário começa em (68,612), grid 8x5 visível, tooltip alinha ao cursor, ícones não pixelam (use UI Texture Group), textos legíveis em 100%/125% de escala.

Guia ultra-detalhado (cliques + nós Blueprint)

Use esta seção como roteiro “faça você mesmo” para iniciantes completos, sem saltos de conhecimento.

  1. Estrutura do projeto: Crie pastas Content/UI, Content/Data, Content/Blueprints. No Content Browser, clique com o botão direito → Miscellaneous > Data Asset → escolha a classe PrimaryDataAsset → nomeie DA_ItemTable.
  2. Schema SQL inicial: No seu servidor SQL, execute:
    CREATE TABLE mu_items (
  account_id VARCHAR(64),
  character_id VARCHAR(64),
  slot INT,
  item_id INT,
  qty INT,
  PRIMARY KEY(account_id, character_id, slot)
);
    Isso garante persistência simples 1:1 com os slots do inventário.
  3. Endpoints VaRest prontos: Configure o backend para aceitar:
    POST /api/inventory/load  {"accountId":"A1","characterId":"C1"}
POST /api/inventory/save  {"accountId":"A1","characterId":"C1","slots":[{"slot":0,"itemId":4,"qty":2}]}
    No Blueprint PlayerController, adicione Make Json Object → Set String Field (accountId, characterId) → Call URL (VaRest POST).
  4. Slots replicáveis na prática: No PlayerState Blueprint, adicione uma variável InventorySlots (Array de FItemSlot_BP) marcada como Replicated. Crie um evento OnRep_InventorySlots que percorre (For Each) e chama UpdateSlotWidget.
  5. Montando o slot: Em WBP_InventorySlot, selecione o Button → aba Details → On Clicked → Bind Event. No gráfico, conecte para emitir Dispatcher OnSlotClicked com o índice do slot (exposto via variável SlotIndex).
  6. Drag-and-drop passo a passo: Ainda em WBP_InventorySlot, clique no Button → Overrides → OnDragDetected. No gráfico, adicione nós: Detect Drag if Pressed → Construct Drag Visual (use o Image do ícone) → Set Drag Visual Offset para (-32,-32) para centralizar o cursor.
  7. Chamada RPC sem erros: No PlayerController Blueprint, adicione Custom Event Server_MoveItem (Run on Server, Reliable). Entrada: FromSlot, ToSlot. No corpo, chame ValidateSlot (Branch). Se verdadeiro, atualize o array no PlayerState e chame Multicast_UpdateInventory (Run on Multicast) para todos verem a mudança.
  8. Popular grid por Blueprint: No WBP_Inventory, no Event Construct, crie laço ForLoop de 0 a 39 (40 slots). A cada iteração: Create Widget (WBP_InventorySlot) → Set SlotIndex → Add Child to UniformGrid com Column = Index % 8 e Row = Index / 8. Salve os refs em array SlotWidgets.
  9. Atualizar ícones: No evento UpdateSlotWidget, receba SlotIndex e FItemSlot_BP. Use Get Data Table Row a partir do DA_ItemTable para buscar o ícone. Se ItemId == 0, esconda a imagem (Set Visibility: Hidden) e zere a quantidade.
  10. Persistência de saída: No Event EndPlay do PlayerController, monte o JSON: Make Array de Make Json Object (slot, itemId, qty) → use Set Array Field ("slots") → VaRest POST para /api/inventory/save. Conecte On Request Completed a um Print String verde para confirmar.
  11. Erro visível para usuário: Adicione um TextBlock "Erro: inventário cheio" posicionado em X=68, Y=996. No Server_PickupItem, se o inventário estiver cheio, chame um Multicast_ShowMessage que seta o texto e toca um som UI_Error.
  12. Teste manual guiado: Abra o mapa → pressione I → arraste um item do slot 0 ao 7 → observe highlight azul. Pressione Shift+D (atalho que você configura) para soltar item; valide que o VaRest save é chamado ao sair do mapa (confirme no log Output Log).
  13. Anti-duplicação básico: Crie variável bIsMovingItem (bool replicado). Antes de executar qualquer RPC de move/drop/pickup, faça Branch; se verdadeiro, retorne e mostre mensagem "Aguardando operação anterior". Zere a flag apenas no OnRep_InventorySlots.
