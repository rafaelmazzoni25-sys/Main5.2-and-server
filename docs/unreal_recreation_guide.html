Roadmap Cronológico

Sequência sugerida para portar o cliente/servidor legado para UE5 usando arquitetura server-authoritative e Replication (RPCs/RepNotify/variáveis replicadas). Ignore totalmente o envio manual de pacotes do código antigo.

  1. Core & Networking

    Configurar UGameInstance, AGameMode (somente servidor) e APlayerController para login/handshake inicial via RPCs e variáveis replicadas.

    • Checklist: criação de UGameInstance custom, GameMode dedicado, PlayerState com structs replicadas.
    • Entrega mínima: login funcional com validação server-side e HUD reativo por RepNotify.
    • Como fazer: no editor crie uma classe C++ UGameInstance (Add → New C++ Class) e marque PrimaryAssetId para tabelas. No GameMode, habilite bUseSeamlessTravel e defina PlayerControllerClass. No PlayerController, exponha ServerLogin(FString User, FString Pass) e valide no servidor, retornando ClientLoginResult para atualizar widgets.
  2. Seleção & Lobby

    Criar mapa de login e fluxos de seleção de sala/personagem carregando dados simulados ou tabelados, sempre replicados do servidor.

    • Checklist: tabela de salas/servers, OnRep para slots de personagem e botões de criar/deletar com RPC.
    • Entrega mínima: troca de mapa (lobby → mundo) via ServerTravel com personagem escolhido replicado.
    • Como fazer: crie um Level “LoginMap” e um Widget UMG com painel de servidores. Preencha via DataTable (Add → Misc → Data Table) derivada de FServerRow. No PlayerController, exponha ClientReceiveServers para popular a lista e um RPC ServerSelectServer que seta um struct replicado FSelectedServer. Para personagens, replique um array TArray<FCharacterSlot> e use OnRep para atualizar os botões de seleção.
  3. Mundo & Movimentação

    Preparar catálogos de mapas, NavMesh e movimentação replicada; implementar Gate/Warp como RPC server-side com validação baseada nas tabelas legadas.

    • Checklist: DataTable de mapas/gates, NavMesh funcional, ServerMoveTo validando caminho.
    • Entrega mínima: player consegue caminhar/teleportar com correções server-authoritative visíveis.
    • Como fazer: em cada mapa, coloque um NavMeshBoundsVolume e habilite Rebuild at Runtime. Use ACharacter com CharacterMovementComponent replicado; ative bUseControllerRotationYaw=false para strafe. Crie um Actor AWarpGate com UBoxComponent trigger chamando ServerRequestWarp(TargetGateId); o GameMode consulta a DataTable e chama ServerTravel ou Teleport com SetActorLocation validado.
  4. Dados & RPG

    Estruturar atributos, XP e level up com structs replicadas e lógicas de progressão derivadas das fórmulas do código antigo.

    • Checklist: FCharacterStats replicado, fórmulas de XP/level up portadas, eventos de level up multicast.
    • Entrega mínima: ganhar XP de mock (missão/mob) e subir nível refletindo atributos/FX.
    • Como fazer: defina FCharacterStats em PlayerState com UPROPERTY(ReplicatedUsing=OnRep_Stats). Importe a tabela de XP do legado para um DataTable e implemente ServerAddExperience(SourceTag, Amount) no PlayerController. No OnRep_Stats, atualize o HUD UMG (ProgressBar e TextBlocks) via BindWidget.
  5. Inventário & Itens

    Modelar itens como DataAssets, inventário/baú replicados, troca de malhas visuais e regras de uso conforme o legado.

    • Checklist: UInventoryComponent replicado, DataAssets preenchidos, UI de grid reagindo a OnRep.
    • Entrega mínima: pickup/usar/equipar itens com validação de requisitos e atualização visual.
    • Como fazer: crie um UInventoryComponent C++ (Add → New C++ Class → Actor Component) e registre no GetLifetimeReplicatedProps. Exponha RPCs ServerMoveItem, ServerUseItem. Converta CSV do legado em PrimaryDataAsset via Import Asset. No Character Blueprint, associe sockets (Weapon, Shield, Wing) e no OnRep_Equipment troque USkeletalMeshComponent com SetSkeletalMesh.
  6. Combate & AI

    Spawning de mobs no servidor, AI controller/behavior tree, sistema de skills/dano e drop de itens replicados.

    • Checklist: tabelas de mobs, Behavior Tree básico, GAS configurado, replicação de HP/estado.
    • Entrega mínima: mob ataca/jogador responde e loot dropa com regras de distância/antiflood.
    • Como fazer: habilite o GAS (Plugin) e adicione UAbilitySystemComponent no Character. Crie UDataTable “DT_Mobs” com HP/Attack/MoveSpeed. No mapa, posicione um ASpawnVolume com SpawnMob() que instancia AMonsterCharacter e roda RunBehaviorTree. No UCombatComponent, implemente ServerApplyDamage lendo fórmulas do legado e dispare NetMulticastPlayImpactFX. Para drops, um OnDeath server-side cria ALootActor com FLootEntry replicado.
  7. Economia

    NPC Shops, Trade e CashShop com RPCs e validação server-side, reutilizando tabelas de preços/impostos do legado.

    • Checklist: DataTable de preços/impostos, UI de shop replicada, sessão de trade replicada.
    • Entrega mínima: compra/venda/trade concluindo com logs server-side.
    • Como fazer: crie UDataTable para lojas (itens, preço, imposto). No NPC Blueprint, adicione UWidgetInteraction para abrir UI; o PlayerController chama ServerOpenShop(NpcId) e o GameMode replica FShopStock. Para trade, instancie um Actor replicado APlayerTradeSession contendo arrays de slots e RPCs ServerAddTradeItem/ServerConfirmTrade. No CashShop, use o mesmo fluxo mas aplicando ServerConsumeCurrency com validação.

Instruções Técnicas

Para cada sistema, veja o de/para entre a lógica C++ antiga (fórmulas, tabelas, regras) e a arquitetura replicada da Unreal. Não porte a camada de sockets/pacotes.

1. Core & Networking

  • GameInstance como ponto de bootstrap: O legado inicializa estados globais e envia cabeçalhos de conexão. No UE5, mova essa orquestração para uma subclasse de UGameInstance que armazena configurações (servidor escolhido, idioma, opções). Use um RPC confiável no PlayerController para realizar o handshake de login em vez de pacotes ad hoc. O servidor valida credenciais em C++ e replica um FPlayerLoginState (struct replicada) com RepNotify para atualizar a UI do cliente.
  • GameMode server-only: No código antigo o servidor decide sucesso/erro de login. Em UE5, mantenha AGameMode apenas no servidor e exponha funções ExecLogin(ServerRPC) e ClientLoginResult(ClientRPC). O cliente nunca seta variáveis de sessão diretamente; apenas invoca RPCs.
  • PlayerController e HUD: A UI de login/seleção que antes lia diretamente input agora chama métodos do APlayerController (ou UUserWidget via BlueprintCallable) para enviar RPCs ao servidor. Use OnRep para alterar widgets conforme o estado do login (conectando, sucesso, erro).
  • Fila de reconexão e heartbeats: O legado monitora desconexões por tempo de socket. Em UE5, implemente heartbeats periódicos (ServerRPC + OnRep_LastHeartbeat) para detectar timeouts e forçar SeamlessTravel para lobby em caso de queda.
  • Logs e equivalência com legado: Crie um helper C++ que gera logs no formato do servidor antigo (IDs, resultado de login, IP). Isso facilita comparar comportamento com sessões reais do legado sem reimplementar pacotes.

2. Seleção & Lobby

  • Mapa de Login e Seleção de Sala: No legado, o usuário escolhe servidor/sala antes de entrar. Em UE5, abra um mapa de lobby (carregado por OpenLevel) que instancia um widget de lista de salas. A lista vem de uma tabela (ex-w_MapHeaders ou configs) replicada via FServerInfo array em GameState. Selecionar sala envia ServerSelectWorld(ServerRPC); o servidor responde com ClientWorldAccepted.
  • Seleção de Personagem: As structs antigas retornavam slots com classe, level e visual. Converta essas structs em um FCharacterSlotData replicado pelo servidor no PlayerState. O widget de seleção lê via OnRep_CharacterSlots. Botões de criar/deletar chamam RPCs que editam a lista no servidor e replicam o resultado.
  • Transição para o mundo: Ao confirmar personagem, o servidor chama ServerTravel ou SeamlessTravel. Antes de viajar, o PlayerController recebe via ClientRPC os dados iniciais (atributos base, inventário vazio ou mock) serializados de tabelas legadas.
  • Sincronização de tempo e clima: O legado envia pacotes de tempo; em UE5, replique um FWorldTimeState no GameState para hora/clima e use OnRep para acionar MaterialParameterCollection que ajusta iluminação.

3. Mundo & Movimentação

  • Catálogo de mapas e streaming: Em vez de instanciar classes de mapa manualmente, crie um DataTable de mapas (ID → ULevel/DataLayer). O servidor escolhe o subnível a streamar e replica o ID atual no GameState. Clientes usam OnRep_CurrentMapId para carregar o nível correspondente.
  • NavMesh e movimento replicado: A lógica antiga quantiza direções (DirTable) e empacota passos. Em UE5, confie no CharacterMovementComponent: o cliente apenas solicita destino com ServerMoveTo(ServerRPC); o servidor valida no NavMesh e move (ou ajusta) usando AAIController ou MoveToLocation. O MovementComponent já replica posição/rotações; use OnRep para eventos como início/fim de dash.
  • Gate/Warp: A tabela CMoveCommandData descreve requisitos. Migre para DataTable (level dest, level mínimo, custo, coords). Triggers no mapa chamam ServerRequestWarp, o GameMode valida contra a tabela e usa ServerTravel ou teleporte instantâneo (SetActorLocation) aplicando custo. Clientes apenas reagem a ClientWarpResult.
  • Segurança de movimentação: Para evitar speed hack, compare ClientTimeStamp com distância percorrida no servidor (equivalente ao anti-cheat do legado) e aplique correção suave usando ClientAdjustPosition.

4. Dados & RPG

  • Structs de atributos replicados: O legado usa campos em CHARACTER (Str, Agi, Vit, Energy, Command, level, dinheiro). Crie um FCharacterStats marcado com UPROPERTY(ReplicatedUsing=OnRep_Stats) no PlayerState. Apenas o servidor altera; o cliente recebe por RepNotify e atualiza HUD.
  • XP e Level Up: Reaproveite as fórmulas/tabelas de XP (ex.: EXPERIENCE_COMMON, EXPERIENCE_QUEST). No servidor, mantenha um FExperienceProgress replicado. Funções ServerAddExperience aplicam bônus por fonte, verificam limites (MAX_CHARACTER_LEVEL=400) e disparam OnLevelUp multicast para FX e UI.
  • Visual de equipamentos e asas: Arrays como wingLeft/wingRight definem sockets. Em UE5, configure sockets equivalentes e replique apenas o identificador de item equipado (ex.: EquippedWingId). OnRep_EquippedWing troca a USkeletalMesh ou spawn de NiagaraComponent, evitando replicar meshes inteiras.
  • Buffs/Estados temporários: Buffs do legado (ex.: poções, scrolls) viram GameplayEffects com duração. Replicar tags ativas no PlayerState; aplicar/remover apenas pelo servidor e usar OnRep para atualizar HUD e VFX.

5. Inventário & Itens

  • Itens como DataAssets: Converta as colunas de ZzzInventory em um UPrimaryDataAsset (FItemDefinition) contendo requisitos, tipo, raridade e VFX. IDs do legado viram PrimaryAssetId. O servidor instancia FItemInstance (stack, durabilidade, options) e replica arrays.
  • Inventário replicado: Crie um UInventoryComponent com TArray<FItemInstance> marcado como ReplicatedUsing=OnRep_Inventory. Operações de mover/usar item são RPCs servidor-side; o servidor valida regras do legado (IsTradeBan, IsDropBan, slots extras). UI em UMG escuta OnRep e redesenha a grid (UniformGridPanel).
  • Warehouse/Baú: Mantenha componente separado (UStorageComponent) replicado apenas quando a janela abre. A lógica antiga bloqueava inventário durante shop; replique com flags replicadas (bIsShopOpen) que desabilitam drag/drop via Bindings no Widget.
  • Equipamentos visuais: O servidor é dono do estado de equipamento. Ao equipar, chame ServerEquipItem; quando válido, o servidor atualiza atributos e replica um FEquipmentVisuals (IDs) para que o Character troque malhas nos sockets.
  • Logs e auditoria de itens: Reproduza a auditoria do legado registrando quem/onde/quando para cada criação/consumo de item. Use ServerRPC para qualquer alteração e gere logs no servidor (CSV/JSON) para confronto com o comportamento antigo.

6. Combate & AI

  • Spawning e AI server-side: Em vez de spawnar via tabelas em cliente, use o servidor para ler a planilha de mobs (HP, move speed, agressividade) e spawnar APawn com AAIController. Replicar apenas estado necessário (HP, estado de alvo, animação atual via tags).
  • Sistema de skills/dano: Reaproveite fórmulas do legado (dano físico, mágico, taxa de crítico). Implementar via GameplayAbilitySystem: habilidades chamam ServerActivateAbility, o servidor calcula dano e envia NetMulticast para VFX. Use ReplicatedUsing para barras de HP/MP.
  • Sincronização de ação: Estados ACTION_ATTACK, ACTION_MOVE, ACTION_DIE viram GameplayTags replicadas no Character. OnRep_ActionTag toca a montagem/animação apropriada. Evite pacotes de posição; confie no CharacterMovementComponent e ajuste com ServerCheckClientError se necessário.
  • Drop de itens: Quando um mob morre, o servidor consulta as tabelas de drop do legado e spawna AActor de loot com UReplicatedDynamicMeshComponent simples e UBoxComponent para pickup. O claim é via ServerPickupItem com validação de distância e peso.
  • Antiflood e cooldown: O legado limita uso de skills por tempo. No UE5, adicione controles no servidor (cooldown per-skill no GAS, ServerRPC com CheckCooldown) e retorne ClientCooldownRejected se violado.

7. Economia

  • NPC Shops: Inventários de NPCs são tabelas do legado carregadas no servidor. Ao abrir shop, o servidor replica um FShopStock (itens e preços) para o PlayerController. Compras chamam ServerBuyItem e o servidor verifica MAX_MONEY e impostos (g_nTaxRate, g_nChaosTaxRate) antes de debitar.
  • Trade jogador-jogador: Implementar sessão de trade como um objeto replicado (APlayerTradeSession) que mantém slots e confirmações. Toda mudança de slot é RPC server-side; o servidor replica o estado para ambos os clientes. Confirmação dupla dispara transferência e logs.
  • CashShop e Jewels: Itens premium seguem a mesma lógica de DataAsset. Compras são RPCs servidor-side; o servidor aplica bônus (ex.: Jewels de upgrade) via GameplayEffect garantindo que as regras de falha/sucesso do legado sejam respeitadas e replicando apenas o resultado (novo nível do item, FX via multicast).
  • Impostos dinâmicos e eventos: Se o legado varia tax rates por evento, replique FTaxState no GameState e use OnRep para UI de shop. Eventos de desconto podem ser aplicados via ServerRPC acionado por GM tools.

8. Testes e Depuração

  • Validação cruzada com logs do legado: Rode casos simples (login, pickup, level up) registrando CSV no servidor UE5 e compare com sessões do servidor antigo para garantir paridade.
  • Checagens de replicação: Use Net PktLag e Net PktLoss no editor para validar comportamento com latência e perda; priorize Reliable apenas para eventos críticos (login, compra).
  • Automação mínima: Crie testes funcionais em Spec ou Gauntlet que percorrem login → seleção → combate → compra para evitar regressões de RPC.

9. Dimensões e Layouts de UI Legados

Replique a ergonomia do cliente antigo definindo tamanhos e ancoragens equivalentes; ajuste por resolução usando DPI Scaling no Project Settings → User Interface.

  • HUD (barra inferior): Base 800×600 → faixa inferior 800×96 px (12% da tela). Health/Mana/SD: barras de 200×14 px com padding 12 px entre elas; painel de hotkeys 10 slots de 48×48 px com gap de 6 px. Em resoluções maiores, ancore em Bottom Stretch e mantenha altura relativa (0.12).
  • Status/Character Window: Janela de ~280×360 px, separada em duas colunas (rótulo 110 px, valor 150 px). Botões de adicionar ponto: 20×20 px alinhados à direita; foto/preview do personagem em SizeBox de 140×180 px. Use Canvas Panel com Slot fixo e ScaleBox para manter proporção.
  • Inventário: Janela ~360×440 px (ver detalhe na aba Inventário). Quando combinar com Status (layout do legado lado a lado), alinhe Inventário à esquerda e Status à direita com espaçamento de 12 px.
  • Warehouse/Baú: Grade 8×15 com slots 32×32 px (total útil 256×480 px) dentro de painel 360×520 px. Adicione barra de rolagem vertical (ScrollBox) se usar mais de 15 linhas.
  • CashShop: Overlay 640×480 px centralizado, dividido em três colunas: árvore de categorias 160 px (à esquerda), lista de itens 280 px (centro, cards 120×64 px), detalhe do item 180 px (direita). Header com saldo em 640×48 px, fonte 16 pt, ícones 24×24 px. Ative Input Mode UI Only e travamento do movimento enquanto aberto.
  • Tooltips: Largura 240–260 px; título 14 pt bold, atributos 12 pt. Use Vertical Box com Padding 10–12 px e limite Wrap Text At em 220 px.
  • Hotbar/Switch rápido: Se o legado exibia duas fileiras (10×2), crie duas Horizontal Box de 10 slots de 48×48 px e espaçamento de 6 px, ancoradas acima do chat (HUD inferior).
  • Proporção e ancoragem: Para preservar dimensões legadas em qualquer resolução, envolva cada janela em SizeBox com Override Width/Height conforme os valores acima, e dentro use ScaleBox (Stretch To Fit, Preserve Aspect Ratio). Configure DPI Curve com 800→1.0, 1080→1.8, 1440→2.2, 2160→3.0 para manter legibilidade.
  • Fluxo de recriação: (1) No UMG, crie Widgets independentes (HUD, Inventory, Status, CashShop). (2) Aplique SizeBox com dimensões do legado. (3) Ancore conforme posição original (ex.: Inventory no canto inferior direito com Alignment 1,1 e Offset negativo de 40 px). (4) Ative Visibility condicional por RepNotify (ex.: bIsShopOpen).

Inventário (Legado ➜ UE5)

Migre a grade e a lógica do inventário/warehouse com replicação nativa, respeitando regras de trava/uso do código legado.

1. Estrutura de dados

  • De: Arrays de slots e flags (IsTradeBan, IsDropBan). Para: UInventoryComponent replicado com TArray<FItemInstance> (slot, stack, durability, options). Use UPROPERTY(ReplicatedUsing=OnRep_Inventory).
  • Warehouse/Baú: UStorageComponent separado, replicado apenas com COND_OwnerOnly. Flags de bloqueio (bIsShopOpen, bIsTradeOpen) replicadas no PlayerState para a UI desabilitar drag/drop.
  • Slots extras: Se o legado libera slots por evento, replique um FInventoryCapacity (tamanho atual/máximo) e atualize a UI via OnRep.
  • Como configurar: No UInventoryComponent, implemente GetLifetimeReplicatedProps, chamando DOREPLIFETIME para o array. No Character Blueprint, adicione o componente e marque Component Replicates. Crie um UUserWidget que recebe uma referência ao componente e se registra em OnRep_Inventory para repintar a grade.

2. Operações (RPCs)

  • Pickup: ServerPickupItem(AActor* Loot) valida distância/peso e aplica anti-double-pick com FGuid por drop. No sucesso, adiciona ao inventário e chama OnRep_Inventory.
  • Mover/Stackar: ServerMoveItem(SrcSlot, DstSlot) centraliza lógica de mescla, swap e limites de stack. Replique apenas o array final; HUD UMG reconstrói a grade no OnRep.
  • Usar/Equipar: ServerUseItem(Slot) verifica requisitos (level, classe, IsDropBan) e dispara efeitos (buffs/consumos) via GameplayEffect. Equipar chama ServerEquipItem e replica IDs visuais (FEquipmentVisuals).
  • Warehouse: ServerMoveToStorage e ServerMoveFromStorage respeitam taxas/custos do legado e usam COND_OwnerOnly para replicação.
  • Como implementar: Para cada RPC, marque com UFUNCTION(Server, Reliable) e adicione funções _Implementation. No servidor, valide pré-condições (peso máximo, bloqueios) e retorne resultados via ClientInventoryResult(EInventoryResult). Em Blueprints, exponha eventos OnRep_Inventory e ClientInventoryResult para tocar sons/FX de sucesso ou erro.

3. UI e feedback

  • Grid: UniformGridPanel populado por OnRep_Inventory. Feedback de erro via ClientInventoryResult (ex.: inventário cheio).
  • Tooltips: Consomem o FItemInstance + FItemDefinition (DataAsset) para exibir requisitos e opções. Atualize automaticamente quando OnRep_Inventory disparar.
  • Logs/Auditoria: Cada alteração chama função server-side de log (JSON/CSV) para rastrear quem/onde/quando, espelhando o legado.
  • Passo-a-passo no UMG: Crie Widget Blueprint “WBP_Inventory”. Adicione UniformGridPanel, Overlay para tooltips e Binding para o componente. No Event Construct, armazene a referência ao UInventoryComponent. Implemente evento custom RefreshGrid chamado por OnRep_Inventory para criar child widgets por slot e associar drag/drop.
  • Dimensões legadas: Para base 800×600 do cliente antigo, use painel principal de ~360×440 px com bordas de 6–8 px. Grade 8×8 com slots de 32×32 px (ícones 30×30 + 1 px de padding). Em 1080p, aplique DPI Scale ≈ 1.8 ou ancore o SizeBox em percentuais para manter proporção. Tooltips: largura fixa 240–260 px, altura variável, com Padding 12 px e textos de 12–14 pt.

AI/Mobs & Drops

Implemente spawn/AI/drops de forma server-authoritative, reutilizando as tabelas do legado para atributos e loot.

1. Spawning

  • De: Spawns definidos em tabelas e acionados pelo servidor legado. Para: Spawners AActor no mapa que leem DataTables de mobs (HP, MoveSpeed, AggroRange, RespawnTime). O servidor chama SpawnMob() e agenda respawn com FTimerManager.
  • Randomização controlada: Use seeds do servidor para variações (nível, prefixos). Nunca deixe o cliente gerar spawn.
  • Visibilidade: Replicar somente estado essencial: HP, tag de ação, alvo atual (Actor pointer replicado), evitando replicar behavior tree.
  • Como configurar spawner: Crie Blueprint “BP_SpawnVolume” derivado de AActor com BoxComponent e variáveis MobId, SpawnCount, RespawnTime. No BeginPlay (apenas servidor), leia DT_Mobs e chame SpawnMob(), guardando ponteiros em um array replicado de fraca referência (TWeakObjectPtr não replica, use TArray<TObjectPtr<AActor>> com COND_None).

2. AI

  • Behavior Tree: Converta FSM simples do legado em Behavior Tree com Blackboard (estado: Idle, Patrol, Chase, Attack, Flee). AAIController roda apenas no servidor.
  • Navegação: Use AI MoveTo com NavMesh; clientes recebem posição replicada via CharacterMovementComponent.
  • Threat/Aggro: Mantenha lista de ameaça em C++ no servidor (dano recente, cura recebida). Escolha alvo por maior threat ou proximidade, replicando apenas o pointer do alvo.
  • Como montar Behavior Tree: Crie Blackboard Keys TargetActor, HasLineOfSight, HomeLocation. No Behavior Tree, adicione sequência de Patrulha (MoveTo → Wait), transição para Perseguição quando TargetActor válido, e nó de Task_ApplyDamage custom chamando ServerApplyDamage. Use um Service que verifica distância e atualiza ameaça a cada 0.5s.

3. Combate & Drops

  • Dano: Use fórmulas do legado (físico/mágico/crit) em um UCombatComponent server-side. RPC ServerApplyDamage recebe o Ability/Skill e executa cálculo; NetMulticast envia VFX/hit reactions.
  • Morte: OnDeath no servidor chama tabela de drop do legado e spawn de ALootActor com UBoxComponent. Replicar um FLootEntry (ItemId, quantidade, raridade) para o dono elegível.
  • Proteção de loot: Respeite regras de posse (ex.: quem deu o último hit). Guarde OwnerPlayerId no drop e só permita pickup via ServerPickupItem se autorizado ou após tempo de liberação.
  • Antiflood/cooldown: Aplique checagem de ataque/skill no servidor com timestamps; rejeite uso fora do cooldown com ClientCooldownRejected.
  • Passo-a-passo de loot: Em ALootActor, adicione UStaticMeshComponent simples para visual. Marque o Actor como replicado e defina bNetUseOwnerRelevancy=true se houver loot privado. No BeginPlay, atribua FLootEntry e um FTimerHandle para destruir após tempo limite. O UBoxComponent chama ServerPickupItem apenas para o PlayerController que sobrepõe e passa validações.

Sistema de Itens

Detalha a modelagem completa de itens e suas regras, convertendo colunas/tabelas do legado para DataAssets e instâncias replicadas.

1. Definição

  • De: Estruturas como ITEM_ATTRIBUTE e tabelas de drop/upgrade. Para: UPrimaryDataAsset (UItemDefinition) com campos: tipo (consumível, equipamento, joia), requisitos (classe/level/força), stats base, durabilidade, raridade, VFX/SFX.
  • IDs: Mapeie o ID do legado para PrimaryAssetId; use FGameplayTag para tipo/subtipo (Weapon/Sword, Armor/Plate).
  • Stacks e opções: Crie FItemInstance com quantidade, durability, opções/atributos randômicos. Marque como replicado e serializável.
  • Como criar DataAssets: No Content Browser, Add → Misc → Primary Data Asset usando a classe UItemDefinition. Importe CSV do legado (File → Import Into Level) e selecione a classe de row FItemDefinitionRow. Preencha campos de requisitos, ícone e referências de mesh/FX.

2. Uso e efeitos

  • Consumíveis: Viram GameplayEffects (cura, buff temporário). ServerUseItem aplica efeito e decrementa stack; OnRep_Inventory atualiza UI.
  • Equipamentos: Ao equipar, aplique modificadores persistentes (ex.: +Str, +Defense) via GameplayEffect com duração infinita. Visual é trocado usando IDs replicados para malhas e partículas.
  • Joias/Upgrades: Codifique probabilidades de sucesso/falha conforme tabela do legado. ServerUpgradeItem calcula resultado, consome recursos e replica novo nível/estado. Reaja no cliente com VFX multicast.
  • Como mapear fórmulas: Crie uma classe helper UItemMathLibrary com funções estáticas CalculateDamageBonus, CalculateUpgradeChance. Copie as constantes do legado (ex.: CHAOS_SUCCESS_RATE) para Config/DefaultGame.ini ou DataTable. Chame essas funções somente no servidor dentro das RPCs de uso/upgrade.

3. Integrações

  • Drop/loot: ALootActor referencia FItemInstance gerado pelas tabelas de drop. Pickup reutiliza a lógica de inventário.
  • Economia: NPC shops consomem UItemDefinition; preços/impostos do legado viram DataTables referenciadas pelo servidor.
  • Persistência: Salve apenas IDs e atributos variáveis do FItemInstance (stack, dura, options) em vez de serializar meshes.
  • Checklist de integração: (1) Adicione coluna de preço/imposto na DataTable do item. (2) No ShopManager server-side, consuma UItemDefinition para montar FShopStock. (3) Em ALootActor, serialize apenas ItemId e atributos variáveis. (4) No salvamento, grave ItemId, quantidade e options como JSON para recriar FItemInstance ao carregar.

4. Dimensões de UI de Itens

  • Ícones: Padronize 32×32 px (ou 64×64 para HD) e habilite mipmaps para escalonamento suave. Use Image em SizeBox de mesmo tamanho para evitar deformação.
  • Cards de listagem (Shop/CashShop): 120×64 px com margem 6 px; imagem 48×48 px à esquerda, textos alinhados à direita. Botão “Comprar” 72×28 px.
  • Tooltip de item: 240–260 px de largura, blocos de texto com Wrap Text At 220 px; seções separadas por Separator de 1 px com margem 8 px.
