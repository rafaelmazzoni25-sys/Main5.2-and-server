Bootstrap Win32 ➜ Blueprint

Controle de MP3 (PlayMp3/StopMp3/IsEndMp3)

O cliente legado liga/desliga música verificando m_MusicOnOff, evita reiniciar a mesma faixa e zera o buffer quando a faixa muda.【F:Source Main 5.2/source/Winmain.cpp†L124-L163】

  1. No GameInstance Blueprint, crie variável bMusicOn (bool) e CurrentTrack (Name).
  2. Função BP_PlayMp3 (evento personalizado): Branch em bMusicOn; se falso e bEnforce for falso, retorna. Compare CurrentTrack com parâmetro TrackName; se igual, retorna. Caso contrário, chame Play Sound 2D com TrackName, salve em CurrentTrack.
  3. Função BP_StopMp3: Branch em bMusicOn ou bEnforce. Se CurrentTrack == TrackName, chame Stop na referência do Audio Component e limpe CurrentTrack.
  4. Função BP_IsEndMp3: Use Get Playback Time & Get Duration do componente; compare igualdade para imitar wzAudioGetStreamOffsetRange()==100.
  5. ADAPTAÇÃO OBRIGATÓRIA PARA UE5: substituir wzAudio por Sound Cue + Audio Component; manter nome da faixa para comparações.
CheckHack ➜ RPC de Ping

A rotina chama SendCheckOnline quando conectado e logado.【F:Source Main 5.2/source/Winmain.cpp†L168-L175】【F:Source Main 5.2/source/ProtocolSend.cpp†L154-L164】

  1. No PlayerController Blueprint, crie evento OnLoggedIn que dispara um Server RPC Server_SendCheck.
  2. No Server_SendCheck, chame Multicast ou Server função C++ que publica um NetMulticast Ping replicando a chamada de SendPingTest.
  3. Use Timer by Function Name para repetir a cada 10s (equivale à checagem periódica).
  4. ADAPTAÇÃO OBRIGATÓRIA PARA UE5: Sockets diretos viram RPC replicado; manter cabeçalho BOTH_CONNECT_LOGIN nos payloads enviados pelo C++ auxiliar.
  5. Fluxo de nós (Blueprint): OnLoggedIn ➜ Set Timer by Function Name (1ª chamada imediata, looping 10s) ➜ função BP_SendCheck ➜ Switch Has Authority ➜ (Server) chama RPC Server_SendCheck ➜ (Server) chama SendPingNative (C++).

Input e Estados do Mouse

Update() ➜ Enhanced Input

O CInput::Update recalcula delta de cursor, limita à tela e rastreia clique simples/duplo para cada botão, respeitando modo left-hand e bloqueio de edição de texto.【F:Source Main 5.2/source/Input.cpp†L60-L234】【F:Source Main 5.2/source/Input.h†L53-L94】

  1. Crie Input Mapping Context com ações MouseLeft, MouseRight, MouseMiddle (trigger Input Down/Up) e LookAxisX/Y (mouse delta).
  2. No PlayerController Blueprint, mantenha variáveis CursorDelta, PrevCursorPos, DoubleClickInterval, LastClickTimes[3], bLeftHandMode, bTextEditMode.
  3. Evento Tick: se bTextEditMode for falso, leia Get Mouse Position on Viewport; use Clamp Vector2D para limites de tela e derive CursorDelta = Pos-Prev. Atualize PrevCursorPos.
  4. Ação MouseLeft (Pressed): calcule Now-LastClickTimes[0]; se ≤ DoubleClickInterval e bFormerBtn0Dn verdadeiro, marque bLBtnDbl; senão marque bLBtnDn. Em modo canhoto, redirecione flags para botão direito.
  5. Ação MouseLeft (Released): se flag de held estiver ativo, marque bLBtnUp e limpe held. Repita a mesma lógica para MouseRight e MouseMiddle seguindo os estados do código legado.
  6. Em cada atualização, quando CursorDelta != 0, limpe bFormerBtn* (evita duplo clique, igual ao código original).
  7. Exponha funções Blueprint IsLBtnDn/Held/Up/Dbl etc. para widgets, mapeando diretamente os getters do C++.
  8. Fluxo de nós (Pressed/Released): Input Action MouseLeft ➜ Sequence (Pressed/Released branches) ➜ Branch bTextEditMode (bloqueio) ➜ Branch bLeftHandMode (swap flags) ➜ Subtract Float com LastClickTimes[idx] ➜ Branch com DoubleClickInterval ➜ set flags bLBtnDbl / bLBtnDn / bFormerBtn* ➜ SetArrayElem para atualizar timestamps.
  9. Fluxo de nós (Tick): Event Tick ➜ Switch Has Authority (apenas cliente) ➜ Get Mouse Position on Viewport ➜ Clamp Vector2D ➜ Vector2D - Vector2D (delta) ➜ Branch para limpar duplos se delta ≠ 0 ➜ salvar PrevCursorPos.

Assets BMD ➜ UE (Conversão FBX)

Limites e Flags

O cabeçalho BMD define limites de ossos/malhas/vértices e flags de renderização como RENDER_NODEPTH, RENDER_CHROME, RENDER_BRIGHT, além dos scripts de textura (TextureScript) com brilho, ocultação e sombra.【F:Source Main 5.2/source/ZzzBMD.h†L6-L199】【F:Source Main 5.2/source/TextureScript.h†L15-L64】

  1. ADAPTAÇÃO OBRIGATÓRIA PARA UE5: a UE5 não lê BMD diretamente. Converta cada BMD para FBX (via ferramenta externa ou script de conversão) mantendo pesos/nomes de ossos e pivôs originais antes da importação.
  2. Importe o FBX respeitando MAX_BONES=200, MAX_MESH=50, MAX_VERTICES=15000; valide em um Editor Utility Widget que rejeite arquivos fora do limite.
  3. Crie Material Functions para cada flag: RENDER_NODEPTH ➜ desligar Depth Test; RENDER_CHROME/CHROME* ➜ Fresnel + Reflection; RENDER_BRIGHT ➜ emissivo; RENDER_OIL ➜ panner + refração.
  4. Converta TextureScript em DataAsset Blueprint contendo Bright, HiddenMesh, StreamMesh, NoneBlendMesh, ShadowMesh. Cada malha (SkeletalMesh ou StaticMesh) referencia o DataAsset e ativa funções de material conforme as flags.
  5. ADAPTAÇÃO OBRIGATÓRIA PARA UE5: ShadowMesh vira Cast Shadow no componente; StreamMesh vira Stream Distance em Render → LOD.
  6. Validação automática (nós): For Each Asset ➜ Get Num Bones/Vertices ➜ Branch se excede constante ➜ Print String + Mark Asset for Deletion (imita rejeição do loader C++).
Actions (Animações)

Action_t traz Loop, PlaySpeed e NumAnimationKeys que devem guiar a configuração das Animation Sequences.【F:Source Main 5.2/source/ZzzBMD.h†L120-L133】

  1. Crie Animation Blueprint com DataTable de ações; cada linha define Loop (bool), PlayRate (float) e número de frames.
  2. Ao importar cada FBX, crie uma Sequence por ação e ajuste Rate Scale para PlaySpeed. Marque Loop Animation quando Loop=true.
  3. Na State Machine, use enum eActionType (servidor) como chave para selecionar a Sequence correspondente (ex.: ACTION_MOVE1 para movimento).

ADAPTAÇÃO OBRIGATÓRIA: Conversão de Coordenadas

Mapeamento Z-up (OpenGL) ➜ UE5

O cliente legado renderiza via OpenGL e traduz a câmera com glTranslatef(-Pos[0], -Pos[1], -Pos[2]), indicando um sistema onde Position[0]=X (direita), Position[1]=Y (cima), Position[2]=Z (profundidade para frente).【F:Source Main 5.2/source/UIWindows.cpp†L1786-L1795】 Na UE5, o sistema é Left-handed com X=frente, Y=lado, Z=cima.

  1. ADAPTAÇÃO OBRIGATÓRIA PARA UE5: Rotação de Eixos Aplique rotação de +90° em X e +90° em Z para alinhar: UE.X = Legacy.Z, UE.Y = Legacy.X, UE.Z = Legacy.Y. Em Blueprint, implemente macro BP_ConvertLegacyVec3 (Vector ➜ Vector) com Make Vector rearranjando componentes e Negate Float quando necessário para manter a mão esquerda.
  2. Para rotadores, use Make Rot From ZX combinando Yaw = LegacyRotY, Pitch = LegacyRotZ, Roll = LegacyRotX e aplique Add Rotator (Yaw +90, Roll -90).
  3. Fluxo de nós (macro): Input LegacyVector ➜ Break Vector (X,Y,Z) ➜ Make Vector (X = Z, Y = X, Z = Y) ➜ opcional Float * -1 no novo Y se notar inversão de sentido lateral.
  4. Use a macro antes de alimentar SetWorldLocation, Add Movement Input e SpawnActor para todos os dados vindos de rede/arquivos do legado.

Sistema Modular de Personagem

Slots e Partes (BodyPart/Weapon/Wing)

O legado mantém arrays BodyPart[MAX_BODYPART], Weapon[2], Wing, Helper e Flag com campos Type, Level, LinkBone e CurrentAction para cada parte.【F:Source Main 5.2/source/w_CharacterInfo.h†L214-L244】 O Script_Item define m_byItemSlot que indica o slot de uso (cabeça, armadura, arma etc.).【F:Source Main 5.2/source/_struct.h†L20-L36】

  1. Crie em UE5 um DataTable (RowStruct FItemSlotRow) com colunas ItemID, Slot (enum cabeça, armadura, asa, armaD, armaE), Mesh (Skeletal/Static), MaterialOverrides, SocketName.
  2. Crie Blueprint Enum EBP_ItemSlot com a ordem do legado (HEAD, ARMOR, WEAPON_R, WEAPON_L, WING, HELPER, FLAG).
  3. No Character Blueprint, mantenha mapa EquippedMeshes (Slot ➜ SceneComponent) e EquippedItems (Slot ➜ ItemID).
Sockets no Skeletal Mesh

Use o Mesh base para definir sockets equivalentes aos ossos do legado (LinkBone):

  1. Abra o Skeletal Mesh do personagem e adicione sockets: Head_Socket (osso cabeça), Body_Socket (spine), WeaponR_Socket/WeaponL_Socket (mãos), Wing_Socket (spine upper), Helper_Socket e Flag_Socket.
  2. Em Blueprint, crie função BP_AttachPart(Slot, Mesh, Materials): usa Add Component (Static ou Skeletal), Set Static/Skeletal Mesh, Set Material e AttachToComponent com SocketName vindo da linha do DataTable.
  3. Fluxo de nós: BP_AttachPart ➜ Switch on EBP_ItemSlot ➜ define SocketName ➜ Add Component ➜ AttachToComponent (Keep Relative) ➜ salva em EquippedMeshes ➜ atualiza EquippedItems.
Swap/Attach com Replicação

Ao equipar, o legado preenche BodyPart/Weapon e atualiza CurrentAction. Replique usando RepNotify ou Multicast.

  1. No Inventory Widget, ao mover item para slot, chame Server RPC Server_SetEquipment(ItemID, Slot).
  2. Em C++ (último recurso), declare UPROPERTY(ReplicatedUsing=OnRep_Equipment) um mapa TMap ReplicatedEquipment e implemente void OnRep_Equipment() chamando BP_RebuildEquipment(). Justificativa: replicação de mapas não é confiável apenas em Blueprint.
  3. BP_RebuildEquipment percorre ReplicatedEquipment, consulta DataTable e chama BP_AttachPart. Para remover, se um Slot mudar para vazio, chame DestroyComponent no componente salvo.
  4. Para armas duplas, respeite Weapon[2] do legado: se Slot==WEAPON_L ou WEAPON_R, escolha socket respectivo e atualize apenas aquele componente.
  5. Fluxo de replicação: OnDropItemIntoSlot (Widget) ➜ Server_SetEquipment ➜ (Server) atualiza ReplicatedEquipment ➜ (Server) chama Multicast MC_PlayEquipFX(Slot) para efeitos visuais ➜ OnRep_Equipment (clientes) ➜ BP_RebuildEquipment (spawn/attach).
Mapeamento de IDs ➜ Assets

Use a tabela do legado (Script_Item) com campos m_byItemSlot, Damage, Defense para popular o DataTable de assets e manter fidelidade.

  1. Pipeline: ao carregar o jogo, leia DataTable DT_ItemSlots (convertido do CSV legado) ➜ preencha mapa ItemID ➜ Slot, Mesh, Materials no GameInstance.
  2. Quando um item entra no inventário, salve ItemID; ao equipar, faça lookup para recuperar Slot e SocketName e chame Server_SetEquipment.
  3. Para Wing/Helper/Flag, mantenha ordem do legado (Wing, Helper, Flag) garantindo attach nos sockets apropriados.

Rede: ProtocolSend ➜ RPC/Structs

Structs e cabeçalhos

Os pacotes usam o enum ProtocolHead e structs PMSG_CONNECT_ACCOUNT_SEND, PMSG_POSITION_SEND, PMSG_MOVE_SEND, mantendo tamanhos fixos.【F:Source Main 5.2/source/ProtocolSend.h†L7-L153】

  1. Em C++, declare UENUM(BlueprintType) EBP_ProtocolHead espelhando a ordem original.
  2. Declare USTRUCT(BlueprintType) FConnectAccount, FPositionPacket, FMovePacket com UPROPERTY(BlueprintReadWrite) para campos correspondentes. Use uint8 para bytes e TArray<uint8> para path[8].
  3. Exponha funções C++ SendPacketNative que recebem o enum e serializam os structs mantendo endianness e padding.
  4. Código C++ sugerido (último recurso): 
    UENUM(BlueprintType)
enum class EBP_ProtocolHead : uint8 { BOTH_CONNECT_LOGIN = 0x01, BOTH_POSITION = 0x10, BOTH_MOVE = 0x20 };

USTRUCT(BlueprintType)
struct FMovePacket { GENERATED_BODY()
  UPROPERTY(BlueprintReadWrite) uint8 Head; // usa EBP_ProtocolHead
  UPROPERTY(BlueprintReadWrite) uint8 PathNum;
  UPROPERTY(BlueprintReadWrite) TArray<uint8> PathBytes; // 8 bytes fixos
};
    Use-o apenas para o layer de serialização; lógica de montagem fica em Blueprint.
Login (SendRequestLogInNew)

O fluxo preenche conta/senha, aplica BuxConvert, escreve versão/serial e envia cabeçalho BOTH_CONNECT_LOGIN.【F:Source Main 5.2/source/ProtocolSend.cpp†L166-L199】

  1. No Widget WBP_Login, botão "Entrar" chama Server RPC Server_SendLogin com usuário/senha.
  2. No RPC (Blueprint): chame função C++ SendLoginNative que aplica BuxConvert e monta FConnectAccount. Em seguida, chama NetMulticast MC_LoginRequested para feedback UI.
  3. Ao receber resultado, dispare evento OnLoginResult em Blueprint; faça Switch on Byte usando os mesmos códigos (0x00–0xD2) e mostre pop-ups equivalentes.
  4. Fluxo de nós (Widget): OnClicked Entrar ➜ Validate Length ➜ Branch ➜ Server_SendLogin (RPC) ➜ Custom Event OnLoginResult ➜ Switch on Byte (0x00 sucesso chama BP_CheckHack; erros mostram Message Box com textos do legado).
  5. ADAPTAÇÃO OBRIGATÓRIA PARA UE5: BuxConvert fica em C++ (manipula memória byte-a-byte) e retorna TArray<uint8> para ser embutido no struct.
Lista de personagens

A requisição envia PMSG_SIMPLE_RESULT_SEND.result=1 para BOTH_CONNECT_CHARACTER.【F:Source Main 5.2/source/ProtocolSend.cpp†L201-L208】

  1. No Lobby Controller Blueprint, evento OnLoginSuccess dispara Server RPC Server_RequestCharacters.
  2. RPC chama C++ SendCharacterListNative que publica o mesmo byte 1 e espera resposta; resposta alimenta DataTable usado pelo widget de seleção.
  3. Fluxo (Blueprint): OnLoginSuccess ➜ Server_RequestCharacters ➜ SendCharacterListNative (C++) ➜ Async Load DataTable Row para popular WBP_CharacterList ➜ ForEachLoop cria widgets filhos.
Posicionamento e Movimento

Posição manda X/Y simples; movimento compacta path em nibbles, limitando PathNum a MAX_PATH_FIND-1 e adiciona direção alvo no nibble alto do primeiro byte.【F:Source Main 5.2/source/ProtocolSend.cpp†L210-L283】

  1. No Character Blueprint, ao mover via clique, gere arrays PathX/PathY e calcule direções usando tabela DirTable (DataTable de 16 entradas). Use macro Blueprint para limitar PathNum a MAX_PATH_FIND-1.
  2. Construa array de 8 bytes: para cada passo, combine nibbles pares/ímpares com Bit Shift Left e Bitwise OR. Primeiro byte recebe (PathNum-1) em nibble baixo e direção alvo em nibble alto.
  3. Envie via Server RPC Server_SendMove que chama C++ SendMoveNative, replicando o path.
  4. Para sync periódico, evento OnTileChanged envia FPositionPacket com X/Y por BOTH_POSITION.
  5. Fluxo de nós (nibble pack): Macro BuildMoveBytes ➜ ForLoop (0..PathNum-1) ➜ Divide Int by 2 (Floor) para índice do byte ➜ Bitwise And (0x0F) ➜ Shift Left para nibble alto quando índice for ímpar ➜ Bitwise OR no array PathBytes[byteIdx] ➜ ao final, Set Array Elem byte0 = ((TargetDir & 0x0F) << 4) | (PathNum-1).
Recepção (RecvJoinServerNew / RecvLoginNew)

Join server valida versão e popula UI; login trata códigos de erro e dispara CheckHack quando sucesso.【F:Source Main 5.2/source/ProtocolSend.cpp†L287-L419】

  1. No C++ de rede, ao receber pacote, dispare Dynamic Delegates expostos a Blueprint: OnJoinServer (struct com Result, ClientVersion[5]) e OnLoginResult.
  2. No GameInstance Blueprint, vincule aos delegates: se versão divergir, chame widget de erro; se sucesso, chame BP_CheckHack (evento que aciona RPC de ping).
  3. Use Switch on Byte para mapear exatamente os códigos 0x00–0xD2 para mensagens do HUD.
  4. Fluxo de nós (OnJoinServer): Bind Event to OnJoinServer ➜ Branch bVersionMatch (compara array 5 bytes) ➜ (false) Open Level "Patch"; (true) Open Level "Login" ➜ Trigger BP_CheckHack após confirmação.

Servidor & Limites

Timers e Inicialização

O GameServer lê GameServerInfo - Common.dat, seleciona SocketManager ou SocketManagerModern e cria timers de 100 ms a 10 s para AI, eventos e manutenção.【F:Source MuServer Update 15/GameServer/GameServer/GameServer.cpp†L56-L118】

  1. No Server GameMode C++, carregue DataTable GameServerInfo na inicialização. Exponha flag bUseModernSocket (bool) para Blueprint.
  2. No GameState Blueprint, em BeginPlay, use Set Timer by Function Name para rotinas: MonsterAI, MonsterMove, Viewport (100 ms/1 s), AccountLevel (60 s) etc., replicando os intervalos originais.
  3. ADAPTAÇÃO OBRIGATÓRIA PARA UE5: substitua timers Win32 por timers do GameMode; mantenha mesma cadência.
Limites de Usuário e Estados

Limites principais: MAX_OBJECT_USER=1000, MAX_VIEWPORT=75, MAX_CHARACTER_LEVEL=400, MAX_MONEY=2000000000; enums eActionType e eExperienceType dirigem animação e XP.【F:Source MuServer Update 15/GameServer/GameServer/User.h†L14-L196】

  1. Crie Config DataAsset com essas constantes e use em validações de HUD (clamp de dinheiro/level) e relevância de replicação (viewport).
  2. Converta eActionType e eExperienceType em Blueprint Enums; use-os na Animation BP (seções movimento/ataque/dano) e nos cálculos de XP.
  3. Em Blueprints de inventário/economia, aplique Clamp Int para não ultrapassar MAX_MONEY; para progressão, bloqueie níveis acima de 400.
